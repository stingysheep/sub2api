# Debug Report: users.last_active_at appears continuously active

- Symptom: Users 20 and 29 show `last_active_at` close to the current time even when no apparent API-key balance is consumed.
- Root cause: The frontend keeps an authenticated browser session alive with `GET /api/v1/auth/me` every 60 seconds (`frontend/src/stores/auth.ts`). That route is protected by the JWT middleware, which calls `TouchLastActiveForUser`; the service deliberately debounces database writes to once per 10 minutes (`backend/internal/service/user_service.go`). Therefore `last_active_at` means recent authenticated panel activity, not model/API-key usage.
- Production evidence (2026-08-31): The client IP associated with user 29 in audit logs emitted `/api/v1/auth/me` once per minute for at least the observed two-hour window. The client IP associated with user 20 emitted the same pattern. User 20 had four `usage_logs` rows in the observed period; user 29 had none. User 29's only active key had `last_used_at` at 10:11:56, but zero usage rows and zero quota usage.
- Verification: Database samples showed user 29 `last_active_at` advancing at the ten-minute debounce boundary (22:56:56 then 23:06:56) while `/auth/me` continued every minute. The services and containers remained healthy.
- Status: DONE_WITH_CONCERNS. No production change was made. The behavior is expected from the current metric semantics, but the label can mislead operators into treating panel presence as API consumption. A separate product change could rename/split the metric (for example, panel activity versus last API-key use).
